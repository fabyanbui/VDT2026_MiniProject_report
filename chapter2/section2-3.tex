\section{Phân tích yêu cầu hệ thống}

Mục này chuyển các yêu cầu của đề tài thành phạm vi hệ thống cần xây dựng. Hệ thống được xem như một nền tảng Feature Flag thu nhỏ cho ứng dụng web, gồm phần quản trị cấu hình, phần đánh giá flag ở thời điểm chạy và ứng dụng demo chứng minh giá trị của việc tách \textit{deploy} khỏi \textit{release}.

Các stakeholder và actor chính của hệ thống gồm:

\begin{itemize}
    \item \textbf{Quản trị viên}: chịu trách nhiệm tạo project, quản lý Feature Flag, cấu hình rule, kích hoạt kill switch, phân quyền demo và theo dõi toàn bộ lịch sử thay đổi.
    \item \textbf{Nhà phát triển}: chuẩn bị cấu hình rollout, kiểm thử rule, tích hợp Evaluation API hoặc JavaScript SDK vào ứng dụng khách và sử dụng audit/history để đối chiếu khi có sự cố.
    \item \textbf{Người xem}: quan sát project, flag, audit log, lịch sử cấu hình và thống kê evaluation nhưng không được thay đổi cấu hình.
    \item \textbf{Ứng dụng tích hợp Feature Flag}: gửi evaluation request kèm context người dùng không nhạy cảm và dùng kết quả trả về để bật hoặc ẩn tính năng tại runtime.
    \item \textbf{Người dùng cuối của ứng dụng demo}: không trực tiếp quản trị nền tảng nhưng là đối tượng nhìn thấy tác động của các quyết định bật/tắt, targeting hoặc percentage rollout.
\end{itemize}

Từ các actor trên, các trường hợp sử dụng chính được gom thành bốn nhóm. Nhóm quản trị cấu hình bao gồm quản lý project, Feature Flag, rule rollout và kill switch. Nhóm runtime evaluation bao gồm việc ứng dụng khách gọi Evaluation API hoặc SDK để nhận quyết định bật/tắt có reason code. Nhóm quan sát và truy vết bao gồm audit log, lịch sử cấu hình và thống kê số lượt evaluation. Nhóm trình diễn bao gồm các kịch bản global enable/disable, targeting theo role hoặc user, percentage rollout và rollback nhanh mà không cần triển khai lại ứng dụng.

\subsection{Yêu cầu phi chức năng}

Các yêu cầu phi chức năng áp dụng cho cả MVP và các phần khuyến khích, nhằm đảm bảo hệ thống không chỉ có đủ chức năng mà còn có hành vi an toàn, dễ giải thích và phù hợp để trình diễn.

\begin{itemize}
    \item \textbf{Tính đúng đắn và xác định}: cùng một cấu hình và cùng một evaluation context phải luôn cho cùng kết quả. Percentage rollout phải dùng stable hashing trên khóa ổn định, không chứa PII.
    \item \textbf{Mặc định an toàn}: khi project hoặc flag không tồn tại, hoặc khi evaluation không thể hoàn tất đáng tin cậy, hệ thống phải trả \texttt{enabled=false}; trường hợp không tìm thấy phải có reason \texttt{NOT\_FOUND}.
    \item \textbf{Thứ tự ưu tiên rõ ràng}: engine phải tuân thủ precedence thống nhất: flag archived, cấu hình disabled, group kill switch, flag kill switch, global on, các rule targeting có thứ tự và cuối cùng là default off.
    \item \textbf{Tách control plane và data plane}: Dashboard và Management API quản lý cấu hình; Evaluation API và Rule Evaluation Engine phục vụ runtime decision. Ứng dụng khách không được phụ thuộc vào dữ liệu quản trị nội bộ.
    \item \textbf{Truy vết và nhất quán dữ liệu}: mutation quan trọng phải ghi audit log append-only với actor, timestamp, target và snapshot trước/sau trong cùng giao dịch lưu dữ liệu.
    \item \textbf{Hiệu năng evaluation}: Evaluation API cần độ trễ thấp; cache snapshot chỉ là tầng tăng tốc và có thể bị xóa mà không làm mất nguồn sự thật trong database.
    \item \textbf{Bảo mật và quyền truy cập}: Management API cần kiểm tra quyền theo RBAC demo; evaluation context do client gửi chỉ dùng để targeting, không được xem là bằng chứng phân quyền thật.
    \item \textbf{Không xem frontend hiding là lớp bảo vệ}: việc ẩn nút hoặc ẩn trang ở frontend chỉ cải thiện trải nghiệm người dùng; API phục vụ tính năng vẫn cần kiểm tra Feature Flag ở backend trước khi trả dữ liệu hoặc thực thi nghiệp vụ.
    \item \textbf{Bảo vệ dữ liệu cá nhân}: hệ thống ưu tiên stable targeting key và dữ liệu mẫu không nhạy cảm; rollout không phụ thuộc vào thông tin định danh trực tiếp của người dùng thật.
    \item \textbf{Khả dụng cho demo}: seed data, README và Docker Compose phải giúp người chấm khởi chạy lại hệ thống trong môi trường mới với ít bước thủ công.
    \item \textbf{Khả năng bảo trì và mở rộng}: logic evaluation phải tách khỏi controller, có test tự động và có thể mở rộng thêm rule, SDK hoặc backend triển khai khác trong tương lai.
    \item \textbf{Tính dễ dùng của giao diện}: Dashboard phải phân biệt trạng thái quản trị của flag như Enabled, Disabled, Archived với trạng thái runtime On/Off; các thao tác bị chặn bởi quyền phải được hiển thị rõ ràng.
\end{itemize}
