
\section{Thiết kế API}

\subsection{Nguyên tắc thiết kế API}

API của hệ thống được tổ chức theo kiến trúc REST, sử dụng JSON, tiền tố phiên bản \texttt{/v1} và quy ước trường dữ liệu dạng \texttt{camelCase}. Thiết kế hiện tại tách rõ hai nhóm endpoint:

\begin{itemize}
    \item \textbf{Control plane}: các endpoint quản trị project, feature flag, rule, group, sample user, audit log, lịch sử cấu hình và thống kê. Nhóm này yêu cầu bearer token demo và được kiểm tra quyền ở backend.
    \item \textbf{Data plane}: endpoint \texttt{POST /v1/evaluate}. Endpoint này phục vụ runtime evaluation cho demo app và SDK, không yêu cầu bearer token quản trị.
\end{itemize}

Các endpoint quản trị dùng khóa nghiệp vụ ổn định như \texttt{projectKey}, \texttt{flagKey} và \texttt{groupKey} trên URL thay vì yêu cầu frontend phải biết định danh nội bộ. Cách này khớp với source code hiện tại trong các controller NestJS và thuận tiện cho demo, vì người trình bày có thể đọc URL theo đúng ngữ nghĩa nghiệp vụ.

\subsubsection{Versioning đường dẫn API}

Toàn bộ REST API được đặt dưới tiền tố \texttt{/v1}. Một số endpoint chính trong source code hiện tại gồm:

\begin{lstlisting}
POST /v1/evaluate
GET  /v1/projects
GET  /v1/projects/{projectKey}/flags
GET  /v1/projects/{projectKey}/groups
GET  /v1/projects/{projectKey}/audit-logs
GET  /v1/projects/{projectKey}/stats/flags
\end{lstlisting}

Trong phạm vi mini project, chỉ có phiên bản \texttt{v1}. Nếu sau này cần thay đổi không tương thích ngược về request hoặc response, hệ thống có thể bổ sung \texttt{/v2} mà không phá vỡ client đang dùng \texttt{/v1}.

\subsubsection{Phân trang, lọc và sắp xếp}

Các endpoint trả về danh sách sử dụng offset pagination với \texttt{limit} và \texttt{offset}. Giá trị mặc định là \texttt{limit = 20}, \texttt{offset = 0}; \texttt{limit} không vượt quá 100. Response danh sách trong backend hiện tại có dạng:

\begin{lstlisting}
{
  "items": [],
  "page": {
    "limit": 20,
    "offset": 0,
    "total": 42,
    "hasNext": true
  }
}
\end{lstlisting}

Các query filter phụ thuộc từng endpoint. Ví dụ, danh sách flag hỗ trợ \texttt{search}, \texttt{status} và \texttt{lifecycleStatus}; rule hỗ trợ lọc theo \texttt{type}; audit log hỗ trợ lọc theo \texttt{targetType}, \texttt{targetKey}, \texttt{actor}, \texttt{action}, \texttt{from} và \texttt{to}; statistics hỗ trợ \texttt{environmentKey}, khoảng thời gian và sort theo tổng số lượt evaluation.

\subsection{API quản lý project và environment}

Project là phạm vi quản lý cấp cao nhất. Source code hiện tại triển khai các endpoint project sau:

\begin{itemize}
    \item \texttt{GET /v1/projects}: danh sách project;
    \item \texttt{POST /v1/projects}: tạo project;
    \item \texttt{GET /v1/projects/\{projectKey\}}: xem chi tiết project;
    \item \texttt{PATCH /v1/projects/\{projectKey\}}: cập nhật metadata;
    \item \texttt{DELETE /v1/projects/\{projectKey\}}: soft delete project.
\end{itemize}

Endpoint quản lý environment riêng chưa được mở ra trong phiên bản hiện tại. Environment vẫn là một phần của mô hình dữ liệu và seed data, gồm các môi trường như \texttt{production}, \texttt{staging} và \texttt{development}. Evaluation API có thể nhận \texttt{environmentKey}; nếu client không truyền trường này, backend dùng environment mặc định của project. Nhờ đó, hệ thống vẫn chứng minh được khả năng cấu hình theo môi trường mà không làm dashboard phức tạp quá mức.

\subsection{API quản lý Feature Flag}

Feature Flag được quản lý theo phạm vi project và được định danh bằng \texttt{flagKey}. Các endpoint hiện tại gồm:

\begin{itemize}
    \item \texttt{GET /v1/projects/\{projectKey\}/flags}: danh sách flag đang hoạt động;
    \item \texttt{GET /v1/projects/\{projectKey\}/flags/deleted}: danh sách flag đã soft delete;
    \item \texttt{POST /v1/projects/\{projectKey\}/flags}: tạo flag;
    \item \texttt{GET /v1/projects/\{projectKey\}/flags/\{flagKey\}}: xem chi tiết flag;
    \item \texttt{PATCH /v1/projects/\{projectKey\}/flags/\{flagKey\}}: cập nhật metadata và cấu hình runtime của default environment;
    \item \texttt{POST /v1/projects/\{projectKey\}/flags/\{flagKey\}/archive}: archive flag;
    \item \texttt{POST /v1/projects/\{projectKey\}/flags/\{flagKey\}/restore}: restore flag đã archive;
    \item \texttt{DELETE /v1/projects/\{projectKey\}/flags/\{flagKey\}}: soft delete flag;
    \item \texttt{POST /v1/projects/\{projectKey\}/flags/\{flagKey\}/restore-deleted}: khôi phục flag đã soft delete.
\end{itemize}

Khi tạo flag, backend tạo cấu hình \texttt{FlagEnvironmentConfig} mặc định với \texttt{status = DISABLED}, \texttt{servingMode = TARGETED} và \texttt{killSwitch = false}. Khi cập nhật \texttt{status}, \texttt{servingMode} hoặc \texttt{killSwitch}, backend ghi audit log trong cùng transaction và invalidation evaluation snapshot cache của flag liên quan.

Cần phân biệt \texttt{lifecycleStatus} của flag với trạng thái runtime. \texttt{ACTIVE} hoặc \texttt{ARCHIVED} mô tả vòng đời của flag; còn \texttt{enabled} trong Evaluation API là kết quả On/Off tại runtime.

\subsection{API quản lý rule}

Source code hiện tại không dùng endpoint CRUD từng rule riêng lẻ. Dashboard gửi toàn bộ danh sách rule mong muốn cho một flag bằng endpoint replace:

\begin{itemize}
    \item \texttt{GET /v1/projects/\{projectKey\}/flags/\{flagKey\}/rules}: xem rule hiện tại;
    \item \texttt{PUT /v1/projects/\{projectKey\}/flags/\{flagKey\}/rules}: thay thế toàn bộ ordered rule set.
\end{itemize}

Request \texttt{PUT} chứa mảng \texttt{rules}; mỗi rule có \texttt{type}, \texttt{priority}, \texttt{enabled} và \texttt{parameters}. Ba loại rule được hỗ trợ là \texttt{USER\_ALLOWLIST}, \texttt{ROLE\_TARGETING} và \texttt{PERCENTAGE\_ROLLOUT}. Với source code hiện tại, user allowlist dùng \texttt{parameters.userIds}; role targeting dùng \texttt{parameters.roles}; percentage rollout dùng \texttt{parameters.percentage}. Rule bị disable được bỏ qua khi evaluation.

Việc replace toàn bộ danh sách rule giúp UI dễ lưu thứ tự hiện tại và giúp audit log ghi được snapshot trước/sau của toàn bộ rule set bằng action \texttt{FLAG\_RULES\_REPLACED}.

\subsection{API quản lý flag group và group kill switch}

Flag group là chức năng khuyến khích đã được triển khai để hỗ trợ kill switch theo nhóm. Các endpoint chính gồm:

\begin{itemize}
    \item \texttt{GET /v1/projects/\{projectKey\}/groups}: danh sách group;
    \item \texttt{POST /v1/projects/\{projectKey\}/groups}: tạo group;
    \item \texttt{PATCH /v1/projects/\{projectKey\}/groups/\{groupKey\}}: đổi tên group;
    \item \texttt{DELETE /v1/projects/\{projectKey\}/groups/\{groupKey\}}: xóa group;
    \item \texttt{PUT /v1/projects/\{projectKey\}/groups/\{groupKey\}/config}: bật hoặc tắt kill switch của group trong một environment;
    \item \texttt{PUT /v1/projects/\{projectKey\}/flags/\{flagKey\}/group}: gán flag vào group;
    \item \texttt{DELETE /v1/projects/\{projectKey\}/flags/\{flagKey\}/group}: gỡ flag khỏi group.
\end{itemize}

Trạng thái kill switch của group được lưu trong \texttt{FlagGroupConfig} theo từng environment. Khi group kill switch bật, Evaluation Engine trả \texttt{enabled = false} với reason \texttt{GROUP\_KILL\_SWITCH} sau khi đã kiểm tra \texttt{FLAG\_ARCHIVED} và \texttt{FLAG\_DISABLED}, nhưng trước flag-level \texttt{KILL\_SWITCH}, \texttt{GLOBAL\_ON} và các rule targeting.

\subsection{Evaluation API}

Evaluation API là data-plane endpoint công khai của demo:

\begin{lstlisting}
POST /v1/evaluate
\end{lstlisting}

Request body gồm project, flag, environment tùy chọn và evaluation context:

\begin{lstlisting}
{
  "projectKey": "demo-project",
  "environmentKey": "production",
  "flagKey": "new-checkout",
  "context": {
    "targetingKey": "demo-user-beta",
    "userId": "demo-user-beta",
    "roles": ["beta-customer"]
  }
}
\end{lstlisting}

Response luôn chứa \texttt{projectKey}, \texttt{flagKey}, \texttt{enabled}, \texttt{variant}, \texttt{reason} và \texttt{matchedRuleId}:

\begin{lstlisting}
{
  "projectKey": "demo-project",
  "flagKey": "new-checkout",
  "enabled": true,
  "variant": "on",
  "reason": "ROLE_MATCH",
  "matchedRuleId": "rule-id"
}
\end{lstlisting}

Nếu project, environment, flag hoặc flag environment config không tồn tại, API trả evaluation-shaped response an toàn với \texttt{enabled = false}, \texttt{variant = off}, \texttt{reason = NOT\_FOUND}. Nếu percentage rollout được đánh giá nhưng thiếu \texttt{targetingKey}, API trả \texttt{INVALID\_CONTEXT}. Lỗi bất ngờ trong evaluation path được bắt lại và trả \texttt{ERROR} theo nguyên tắc fail-closed.

Các reason code hiện tại gồm \texttt{GLOBAL\_ON}, \texttt{FLAG\_DISABLED}, \texttt{FLAG\_ARCHIVED}, \texttt{GROUP\_KILL\_SWITCH}, \texttt{KILL\_SWITCH}, \texttt{USER\_ALLOWLIST}, \texttt{ROLE\_MATCH}, \texttt{PERCENTAGE\_ROLLOUT}, \texttt{DEFAULT\_OFF}, \texttt{NOT\_FOUND}, \texttt{INVALID\_CONTEXT} và \texttt{ERROR}.

\subsection{API audit log và lịch sử cấu hình}

Audit log được truy vấn trong phạm vi project:

\begin{itemize}
    \item \texttt{GET /v1/projects/\{projectKey\}/audit-logs}: danh sách audit log;
    \item \texttt{GET /v1/projects/\{projectKey\}/flags/\{flagKey\}/history}: lịch sử cấu hình tập trung của một flag.
\end{itemize}

Audit log lưu \texttt{actor}, \texttt{action}, \texttt{targetType}, \texttt{targetId}, \texttt{targetKey}, \texttt{before}, \texttt{after}, \texttt{metadata}, \texttt{requestId} và thời điểm tạo. Các thao tác mutation quan trọng như tạo/cập nhật project, tạo/cập nhật/archive/restore/delete flag, replace rule, tạo/cập nhật group, bật/tắt group kill switch và gán/gỡ group đều ghi audit log cùng transaction với thay đổi nghiệp vụ.

Endpoint history không tạo bảng version riêng. Nó là projection đọc từ \texttt{AuditLogEntry} cho flag, flag environment config và rule liên quan. Cách này đáp ứng yêu cầu lịch sử cấu hình mà không tạo hai nguồn sự thật song song.

\subsection{API thống kê evaluation}

Thống kê evaluation là chức năng khuyến khích đã được triển khai bằng dữ liệu aggregate theo giờ UTC, không lưu raw evaluation context. Các endpoint hiện tại gồm:

\begin{itemize}
    \item \texttt{GET /v1/projects/\{projectKey\}/stats/flags}: tổng hợp theo các flag trong project;
    \item \texttt{GET /v1/projects/\{projectKey\}/flags/\{flagKey\}/stats}: thống kê chi tiết một flag.
\end{itemize}

Dữ liệu thống kê được nhóm theo \texttt{projectKey}, \texttt{environmentKey}, \texttt{flagKey}, \texttt{bucketStart}, \texttt{reason} và \texttt{enabled}. Hệ thống cố ý không lưu targeting key, user ID, role, attributes hay matched rule ID trong bảng metric. Việc ghi metric là best-effort; nếu ghi metric thất bại, Evaluation API vẫn trả kết quả cho client.

\subsection{Validation và mô hình lỗi}

Backend sử dụng DTO, \texttt{class-validator}, \texttt{ValidationPipe} và global exception filter để chuẩn hóa validation và error response. Key nghiệp vụ tuân theo biểu thức chính quy:

\begin{lstlisting}
^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$
\end{lstlisting}

Điều này tương ứng với độ dài 3--64 ký tự, chỉ gồm chữ thường, chữ số và dấu gạch ngang, không bắt đầu hoặc kết thúc bằng dấu gạch ngang. Error response control-plane có dạng:

\begin{lstlisting}
{
  "code": "VALIDATION_ERROR",
  "message": "Request validation failed.",
  "details": [
    { "field": "projectKey", "message": "Invalid key format" }
  ],
  "requestId": "request-id"
}
\end{lstlisting}

Các mã lỗi hiện tại gồm \texttt{VALIDATION\_ERROR}, \texttt{UNAUTHORIZED}, \texttt{FORBIDDEN}, \texttt{NOT\_FOUND}, \texttt{CONFLICT} và \texttt{INTERNAL\_ERROR}. Request ID được lấy từ header \texttt{X-Request-Id} nếu có, hoặc được backend tạo tự động; giá trị này xuất hiện trong error response, audit log và log phía server để hỗ trợ truy vết \cite{owasp_rest_security,owasp_logging}.

\subsection{Tài liệu hóa API}

Backend sinh tài liệu OpenAPI/Swagger từ controller và DTO. Sau khi backend khởi động, Swagger UI có tại:

\begin{lstlisting}
/docs
\end{lstlisting}

Swagger được cấu hình với bearer auth cho control-plane demo token và API key \texttt{X-Request-Id}. Các tag chính gồm Health, Projects, Feature Flags, Rules, Evaluation, Statistics, Sample Users và Audit Logs. Việc sinh tài liệu từ source code giúp báo cáo, frontend, SDK và kiểm thử bám sát hợp đồng triển khai thực tế.
