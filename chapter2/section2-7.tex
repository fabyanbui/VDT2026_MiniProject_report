\section{Thiết kế API}

\subsection{Nguyên tắc thiết kế API}

API của hệ thống được thiết kế nhằm cung cấp giao diện thống nhất cho dashboard quản trị, demo application và các ứng dụng khách tích hợp Feature Flag. Thiết kế ưu tiên tính rõ ràng, khả năng dự đoán, khả năng mở rộng và xử lý lỗi nhất quán. Các endpoint được tổ chức theo tài nguyên nghiệp vụ, sử dụng định dạng JSON và tuân theo các nguyên tắc phổ biến của kiến trúc REST.

\subsubsection{Kiến trúc REST}

Hệ thống sử dụng kiến trúc REST, trong đó project, environment, feature flag, flag configuration, rule và audit log được biểu diễn dưới dạng các resource. Mỗi resource được định danh bằng URL và được thao tác thông qua các HTTP method phù hợp.

Các phương thức HTTP chính gồm:

\begin{itemize}
    \item \texttt{GET}: truy vấn một resource hoặc danh sách resource;
    \item \texttt{POST}: tạo resource mới hoặc thực hiện thao tác evaluation;
    \item \texttt{PATCH}: cập nhật một phần trạng thái hoặc thuộc tính của resource;
    \item \texttt{DELETE}: xóa resource khi việc xóa vật lý được cho phép.
\end{itemize}

Ví dụ, endpoint \texttt{GET /v1/projects} trả về danh sách project, trong khi \texttt{POST /v1/projects} tạo một project mới. Việc cập nhật trạng thái của feature flag được thực hiện bằng \texttt{PATCH} vì request chỉ thay đổi một phần dữ liệu hiện có.

Đối với feature flag, thao tác archive được ưu tiên thay cho xóa vật lý nhằm bảo toàn lịch sử cấu hình và audit log. Do đó, feature flag được archive thông qua endpoint cập nhật trạng thái thay vì bị loại bỏ hoàn toàn khỏi cơ sở dữ liệu.

Evaluation API được thiết kế dưới dạng \texttt{POST /v1/evaluate}. Mặc dù thao tác evaluation không làm thay đổi cấu hình flag, request sử dụng \texttt{POST} vì evaluation context được truyền trong request body và có thể chứa nhiều trường như targeting key, user ID, role và custom attributes. Thiết kế này cũng tránh việc đưa thông tin ngữ cảnh hoặc dữ liệu có khả năng nhạy cảm vào query string \cite{openfeature_evaluation_context,openfeature_flag_evaluation}.

API sử dụng JSON cho cả request và response. Mỗi response trả về HTTP status code phù hợp với kết quả xử lý, đồng thời sử dụng cấu trúc dữ liệu thống nhất để client có thể xử lý một cách dự đoán được.

\subsubsection{Versioning đường dẫn API}

Các endpoint được đặt dưới tiền tố phiên bản \texttt{/v1}. Ví dụ:

\begin{lstlisting}
POST /v1/evaluate
GET  /v1/projects
GET  /v1/projects/{projectId}/feature-flags
GET  /v1/audit-logs
GET  /v1/statistics/feature-flags/{flagId}
\end{lstlisting}

Versioning trên đường dẫn giúp phân biệt rõ ràng giữa các phiên bản API và cho phép hệ thống phát triển mà không làm gián đoạn các ứng dụng khách đang sử dụng phiên bản cũ. Khi xuất hiện thay đổi không tương thích ngược, chẳng hạn thay đổi cấu trúc request, response hoặc ý nghĩa của một trường dữ liệu, hệ thống có thể cung cấp phiên bản mới dưới tiền tố \texttt{/v2}.

Các thay đổi tương thích ngược, như bổ sung trường tùy chọn vào response hoặc thêm endpoint mới, không yêu cầu tăng phiên bản API. Ngược lại, việc xóa trường, đổi tên trường hoặc thay đổi kiểu dữ liệu được xem là breaking change và cần được triển khai trong phiên bản mới.

Trong phạm vi mini project, toàn bộ endpoint sử dụng phiên bản \texttt{v1}. Cách tổ chức này đủ đơn giản cho việc triển khai hiện tại nhưng vẫn thể hiện khả năng mở rộng và duy trì hợp đồng tích hợp trong tương lai.

Quy ước thống nhất giữa URL, DTO và response giúp giảm nhầm lẫn trong quá trình phát triển frontend, backend và SDK.

\subsubsection{Phân trang và lọc dữ liệu}

Các endpoint trả về danh sách resource hỗ trợ phân trang bằng hai query parameter là \texttt{limit} và \texttt{offset}. Trong đó, \texttt{limit} xác định số bản ghi tối đa được trả về và \texttt{offset} xác định số bản ghi cần bỏ qua từ đầu tập kết quả.




Giá trị mặc định của \texttt{limit} là 20, giá trị mặc định của \texttt{offset} là 0 và giá trị tối đa của \texttt{limit} là 100. Việc giới hạn số lượng bản ghi trong mỗi request giúp tránh tải quá nhiều dữ liệu vào bộ nhớ và giảm thời gian phản hồi của API.

Response danh sách bao gồm dữ liệu và metadata phân trang:

\begin{lstlisting}
{
  "items": [],
  "pagination": {
    "limit": 20,
    "offset": 0,
    "total": 125
  }
}
\end{lstlisting}

Các endpoint danh sách có thể hỗ trợ thêm query parameter để lọc dữ liệu theo trạng thái, project, environment hoặc từ khóa tìm kiếm. Ví dụ.



Các điều kiện lọc được kết hợp theo phép hội. Những query parameter không được cung cấp sẽ không tham gia vào điều kiện truy vấn. Backend thực hiện validation giá trị query parameter trước khi truy vấn cơ sở dữ liệu nhằm tránh các điều kiện không hợp lệ hoặc gây tải không cần thiết.

Kết quả danh sách phải có thứ tự xác định. Nếu client không cung cấp tiêu chí sắp xếp, hệ thống sử dụng thứ tự mặc định theo thời điểm tạo giảm dần hoặc theo khóa nghiệp vụ tăng dần, tùy loại resource. Việc xác định rõ thứ tự giúp kết quả phân trang ổn định giữa các request liên tiếp.

\subsubsection{Idempotency và tính nhất quán}

Idempotency thể hiện việc gửi cùng một request nhiều lần nhưng không làm thay đổi kết quả cuối cùng của hệ thống sau lần xử lý đầu tiên. Các endpoint sử dụng \texttt{GET}, \texttt{PUT} và \texttt{DELETE} về nguyên tắc cần có tính idempotent, trong khi \texttt{POST} thường không bảo đảm tính chất này.

Trong hệ thống, các thao tác cập nhật trạng thái bằng \texttt{PATCH} được thiết kế theo hướng idempotent. Ví dụ, việc gửi nhiều lần request đặt trạng thái flag thành \texttt{DISABLED} vẫn tạo ra cùng một trạng thái cuối cùng.



Đối với endpoint tạo resource bằng \texttt{POST}, backend áp dụng ràng buộc duy nhất trên các khóa nghiệp vụ như project key, environment key và flag key. Nếu client gửi lại request tạo resource với cùng khóa, hệ thống trả về lỗi \texttt{409 Conflict} thay vì tạo bản ghi trùng lặp.

Evaluation API có tính idempotent về mặt kết quả khi cấu hình flag và evaluation context không thay đổi. Cùng một project key, environment key, flag key và targeting key phải tạo ra cùng một kết quả evaluation. Đặc biệt, percentage rollout sử dụng hàm băm xác định thay vì giá trị ngẫu nhiên để bảo đảm một người dùng được gán ổn định vào cùng một bucket qua nhiều lần evaluation \cite{launchdarkly_percentage_rollouts}.

Các thao tác thay đổi nhiều resource liên quan, chẳng hạn cập nhật flag configuration và ghi audit log, được thực hiện trong cùng một database transaction. Nếu một bước thất bại, toàn bộ transaction được rollback nhằm tránh trạng thái cấu hình đã thay đổi nhưng audit log chưa được ghi nhận.

Đối với các request cập nhật cấu hình đồng thời, hệ thống sử dụng timestamp cập nhật hoặc version cấu hình để phát hiện dữ liệu cũ. Client không được ghi đè một phiên bản mới hơn bằng dữ liệu được đọc từ phiên bản cũ mà không có kiểm tra phù hợp. Nguyên tắc này giúp hạn chế lost update và duy trì tính nhất quán của cấu hình Feature Flag.

Sau khi mutation thành công, cache liên quan đến project, environment hoặc flag phải được invalidation trước khi request tiếp theo sử dụng dữ liệu mới. Cơ sở dữ liệu được xem là nguồn dữ liệu chính, trong khi cache chỉ đóng vai trò tăng hiệu năng và không được phép trở thành nguồn cấu hình độc lập.

\subsection{API quản lý project và environment}

Project là phạm vi quản lý cấp cao nhất của hệ thống Feature Flag. Mỗi project đại diện cho một ứng dụng hoặc một sản phẩm độc lập và chứa các environment, feature flag, user context mẫu và audit log tương ứng. Environment biểu diễn các môi trường triển khai như development, staging và production, cho phép cùng một feature flag có cấu hình khác nhau theo từng môi trường.

\subsubsection{Cập nhật và archive project}

Thông tin có thể chỉnh sửa của project được cập nhật thông qua endpoint.



Request chỉ cần chứa các trường cần thay đổi.



Project key không được phép thay đổi sau khi khởi tạo vì khóa này có thể đã được sử dụng trong Evaluation API, SDK và cấu hình của các ứng dụng khách. Việc giữ nguyên project key giúp tránh phá vỡ hợp đồng tích hợp và hạn chế yêu cầu cập nhật đồng thời trên nhiều hệ thống.

Mỗi lần cập nhật thành công, backend ghi một audit log chứa actor, request ID, dữ liệu trước thay đổi và dữ liệu sau thay đổi. Việc cập nhật project và ghi audit log được thực hiện trong cùng một transaction để bảo đảm tính nhất quán.

Thay vì xóa vật lý, project được archive thông qua endpoint.



Khi archive, trạng thái vòng đời của project được chuyển từ \texttt{ACTIVE} sang \texttt{ARCHIVED}. Thao tác này không xóa environment, feature flag, rule hoặc audit log thuộc project. Nhờ đó, hệ thống vẫn bảo toàn được lịch sử cấu hình và khả năng truy vết.

Project đã archive không cho phép tạo mới hoặc sửa đổi environment, feature flag và rule. Các endpoint mutation đối với resource thuộc project sẽ trả về \texttt{409 Conflict} hoặc lỗi nghiệp vụ tương ứng. Evaluation API đối với project đã archive trả về kết quả an toàn với trạng thái tắt và reason code phù hợp.

Project có thể được khôi phục thông qua endpoint.



Thao tác archive và restore được thiết kế idempotent. Việc archive một project đã ở trạng thái \texttt{ARCHIVED} hoặc restore một project đang ở trạng thái \texttt{ACTIVE} không tạo ra trạng thái trung gian không hợp lệ.

Quy tắc này giúp ngăn việc xóa ngoài ý muốn toàn bộ cấu hình Feature Flag của một môi trường đang hoạt động.

\subsubsection{Thiết lập environment mặc định}

Mỗi project phải có tối đa một environment mặc định. Environment mặc định được sử dụng khi Evaluation API không nhận được \texttt{environmentKey} từ ứng dụng khách.

Environment mặc định được thiết lập thông qua endpoint.



Request không cần body vì hành động đã được xác định đầy đủ bởi URL. Khi endpoint được gọi, backend thực hiện các bước sau trong cùng một transaction:

\begin{enumerate}
    \item Kiểm tra project và environment có tồn tại;
    \item Kiểm tra environment thuộc đúng project;
    \item Đặt \texttt{isDefault = false} cho environment mặc định hiện tại;
    \item Đặt \texttt{isDefault = true} cho environment được lựa chọn;
    \item Ghi audit log cho thay đổi.
\end{enumerate}

Cơ sở dữ liệu sử dụng partial unique index để bảo đảm chỉ có một environment có \texttt{isDefault = true} trong mỗi project. Ràng buộc ở tầng cơ sở dữ liệu giúp duy trì tính đúng đắn ngay cả khi có nhiều request cập nhật đồng thời.

Ví dụ response.



Nếu environment không thuộc project được chỉ định, hệ thống trả về \texttt{404 Not Found} nhằm tránh làm lộ sự tồn tại của resource ngoài phạm vi truy cập. Nếu project đã archive, thao tác thiết lập environment mặc định bị từ chối.

Khi project chưa có environment mặc định, environment đầu tiên có thể được tự động đặt làm mặc định. Đối với các environment được tạo sau đó, trường \texttt{isDefault} mặc định là \texttt{false}, trừ khi client yêu cầu thiết lập làm mặc định và thao tác được thực hiện thành công trong cùng transaction.

Việc lựa chọn environment mặc định giúp Evaluation API đơn giản hơn đối với các ứng dụng chỉ sử dụng một môi trường. Tuy nhiên, ứng dụng khách triển khai trên nhiều môi trường nên truyền rõ \texttt{environmentKey} để tránh đánh giá nhầm cấu hình.

\subsection{API quản lý Feature Flag}

Feature Flag là tài nguyên trung tâm của hệ thống, đại diện cho một điểm kiểm soát hành vi trong ứng dụng khách. Mỗi flag thuộc về một project, được định danh bằng khóa nghiệp vụ ổn định và có thể sở hữu cấu hình riêng cho từng environment. API quản lý Feature Flag hỗ trợ tạo mới, truy vấn, cập nhật metadata, thay đổi trạng thái vòng đời và quản lý cấu hình runtime theo environment.

\subsubsection{Tạo Feature Flag}

Feature Flag được tạo trong phạm vi một project thông qua endpoint.



Request body gồm khóa định danh, tên hiển thị, mô tả và các thông tin metadata cơ bản.



Trường \texttt{key} là khóa nghiệp vụ được ứng dụng khách sử dụng khi gọi Evaluation API. Giá trị này phải tuân theo biểu thức chính quy:



Flag key phải duy nhất trong phạm vi project. Hai project khác nhau có thể sử dụng cùng một flag key, nhưng trong cùng một project không được tồn tại hai flag có cùng khóa. Sau khi được tạo, flag key không được phép thay đổi nhằm tránh phá vỡ các đoạn mã tích hợp, SDK và request evaluation đang sử dụng khóa này.

Khi tạo flag, backend kiểm tra project tồn tại và đang ở trạng thái \texttt{ACTIVE}. Nếu project đã archive, request bị từ chối vì các resource thuộc project không còn được phép thay đổi.

Response thành công sử dụng mã trạng thái \texttt{201 Created}.



Nếu flag key đã tồn tại trong project, hệ thống trả về \texttt{409 Conflict}. Nếu dữ liệu đầu vào không hợp lệ, hệ thống trả về \texttt{400 Bad Request} cùng thông tin chi tiết về các trường vi phạm validation.

Sau khi flag được tạo, hệ thống có thể tự động tạo các bản ghi cấu hình mặc định cho những environment hiện có của project. Mỗi cấu hình ban đầu sử dụng trạng thái an toàn:

\begin{itemize}
    \item \texttt{status = DISABLED};
    \item \texttt{servingMode = TARGETED};
    \item \texttt{killSwitch = false};
    \item variant mặc định là \texttt{off}.
\end{itemize}

Cách khởi tạo này bảo đảm tính năng mới không được bật ngoài ý muốn ngay sau khi flag được tạo. Nguyên tắc mặc định tắt giúp giảm rủi ro phát hành nhầm và phù hợp với chiến lược fail-safe của hệ thống Feature Flag \cite{unleash_feature_flag_best_practices}.

Thao tác tạo flag và tạo các cấu hình ban đầu được thực hiện trong cùng một database transaction. Nếu một bước thất bại, toàn bộ dữ liệu được rollback để tránh tồn tại flag không có cấu hình môi trường tương ứng.

\subsubsection{Truy vấn danh sách và chi tiết flag}

Danh sách Feature Flag của một project được truy vấn thông qua endpoint.



Endpoint hỗ trợ phân trang, tìm kiếm và lọc theo trạng thái vòng đời.



Kết quả trả về gồm danh sách flag và metadata phân trang.



Kết quả mặc định được sắp xếp theo thời điểm cập nhật giảm dần để các flag vừa thay đổi xuất hiện trước trên dashboard. Client có thể sử dụng các query parameter bổ sung để lọc flag theo environment, trạng thái cấu hình hoặc group khi các chức năng này được hỗ trợ.

Thông tin chi tiết của một flag được truy vấn bằng endpoint.



Response chi tiết bao gồm metadata của flag và danh sách cấu hình theo environment.



Danh sách chi tiết không nhất thiết trả về toàn bộ rule parameter nếu dashboard chưa yêu cầu. Các rule có thể được tải thông qua endpoint riêng nhằm giảm kích thước response và tránh truy vấn dữ liệu không cần thiết.

Nếu flag không tồn tại, hệ thống trả về \texttt{404 Not Found}. Flag đã archive vẫn có thể được truy vấn để phục vụ kiểm tra lịch sử, nhưng response phải thể hiện rõ \texttt{lifecycleStatus = ARCHIVED}.

\subsubsection{Cập nhật thông tin flag}

Metadata của Feature Flag được cập nhật thông qua endpoint.



Request chỉ cần chứa các trường cần thay đổi.



Các trường có thể cập nhật gồm \texttt{name} và \texttt{description}. Trường \texttt{key} không được phép thay đổi sau khi flag được tạo vì đây là định danh được sử dụng trực tiếp trong mã nguồn và Evaluation API.

Backend kiểm tra flag tồn tại, thuộc project đang hoạt động và chưa bị archive. Nếu flag đã archive, thao tác cập nhật metadata bị từ chối cho đến khi flag được restore.

Response thành công trả về trạng thái mới nhất của flag.



Mỗi lần cập nhật tạo một audit log với action tương ứng, thông tin actor, request ID, snapshot trước thay đổi và snapshot sau thay đổi. Việc cập nhật flag và ghi audit log được thực hiện trong cùng một transaction.

Metadata của flag không trực tiếp làm thay đổi kết quả evaluation. Tuy nhiên, sau khi mutation thành công, cache liên quan vẫn có thể được invalidation để bảo đảm các response quản trị và SDK không tiếp tục sử dụng dữ liệu cũ.

\subsubsection{Archive và restore flag}

Feature Flag không được xóa vật lý trong luồng quản trị thông thường. Khi không còn sử dụng, flag được archive thông qua endpoint.



Thao tác archive chuyển \texttt{lifecycleStatus} từ \texttt{ACTIVE} sang \texttt{ARCHIVED}. Các cấu hình, rule, thống kê evaluation và audit log liên quan vẫn được giữ nguyên trong cơ sở dữ liệu.

Trước khi archive, backend kiểm tra trạng thái hiện tại của flag. Nếu flag đang được bật trong một hoặc nhiều environment, hệ thống có thể yêu cầu người quản trị xác nhận hoặc tự động chuyển các cấu hình về trạng thái tắt trước khi hoàn tất thao tác. Trong phạm vi mini project, quá trình archive được thực hiện trong transaction gồm:

\begin{enumerate}
    \item Chuyển trạng thái các cấu hình của flag thành \texttt{DISABLED};
    \item Chuyển vòng đời flag thành \texttt{ARCHIVED};
    \item Tăng version của các cấu hình bị thay đổi;
    \item Ghi audit log cho toàn bộ thao tác;
    \item Invalidate các cache liên quan đến flag.
\end{enumerate}

Evaluation API khi gặp flag đã archive luôn trả về trạng thái tắt.



Flag được khôi phục thông qua endpoint.



Thao tác restore chỉ chuyển vòng đời của flag về \texttt{ACTIVE}. Các cấu hình theo environment vẫn giữ trạng thái \texttt{DISABLED} để tránh tự động bật lại tính năng trên production. Người quản trị phải chủ động kích hoạt từng cấu hình sau khi kiểm tra.

Archive và restore được thiết kế theo hướng idempotent. Gửi lại request archive đối với flag đã archive hoặc restore đối với flag đang active không làm phát sinh trạng thái không nhất quán. Hệ thống có thể trả về trạng thái hiện tại hoặc lỗi nghiệp vụ rõ ràng mà không tạo thêm thay đổi dữ liệu.

Việc archive thay cho xóa vật lý giúp duy trì khả năng truy vết, bảo toàn các tham chiếu audit log và hạn chế nguy cơ tái sử dụng nhầm một flag key cũ. Quản lý vòng đời và loại bỏ các flag không còn sử dụng cũng giúp giảm feature flag debt trong hệ thống \cite{mahdavi_hezaveh_feature_toggles}.

\subsubsection{Quản lý cấu hình theo environment}

Một Feature Flag có thể có nhiều cấu hình, mỗi cấu hình tương ứng với một environment. Cách tổ chức này cho phép cùng một flag được bật trên development, rollout giới hạn trên staging và tắt hoàn toàn trên production.

Cấu hình của flag trong một environment được truy vấn bằng endpoint.



Response gồm trạng thái phục vụ, kill switch, version và danh sách rule.



Cấu hình được cập nhật thông qua endpoint.



Ví dụ request bật flag theo chế độ toàn cục.



Ví dụ request chuyển flag sang chế độ đánh giá theo rule.



Trường \texttt{status} xác định cấu hình có tham gia evaluation hay không. Khi \texttt{status = DISABLED}, Evaluation Engine trả về trạng thái tắt trước khi xét serving mode và các rule.

Trường \texttt{servingMode} có hai giá trị chính:

\begin{itemize}
    \item \texttt{GLOBAL\_ON}: bật tính năng cho toàn bộ context hợp lệ trong environment;
    \item \texttt{TARGETED}: đánh giá tuần tự các rule targeting và percentage rollout.
\end{itemize}

Trường \texttt{killSwitch} có độ ưu tiên cao hơn serving mode và các rule. Khi giá trị này bằng \texttt{true}, flag bị tắt ngay lập tức trong environment tương ứng và Evaluation API trả về reason code \texttt{KILL\_SWITCH}.

Trường \texttt{expectedVersion} được sử dụng để kiểm soát cập nhật đồng thời. Backend chỉ chấp nhận mutation khi version hiện tại của cấu hình trùng với version mà client đã đọc. Nếu không trùng khớp, hệ thống trả về \texttt{409 Conflict} nhằm ngăn một request cũ ghi đè cấu hình mới hơn.

Sau mỗi lần cập nhật thành công, version của cấu hình được tăng lên:



Nếu flag chưa có cấu hình cho environment được chỉ định, hệ thống có thể tạo cấu hình thông qua endpoint.



Request body gồm environment và trạng thái ban đầu.



Backend phải kiểm tra environment và flag cùng thuộc một project. Mỗi cặp \texttt{flagId} và \texttt{environmentId} chỉ được tồn tại một cấu hình duy nhất.

Mọi mutation đối với cấu hình đều được ghi audit log và thực hiện trong transaction. Sau khi transaction hoàn tất, hệ thống invalidates cache theo project, environment và flag để các evaluation tiếp theo sử dụng cấu hình mới nhất. Việc phân tách cấu hình theo environment phù hợp với mô hình quản lý Feature Flag phổ biến, trong đó một flag có thể có trạng thái và targeting rule độc lập trên từng môi trường triển khai \cite{launchdarkly_feature_flags,unleash_feature_flags}.

\subsection{API quản lý rule}

Rule xác định điều kiện để một Feature Flag được bật đối với từng evaluation context. Mỗi rule thuộc về một flag configuration của một environment và được đánh giá theo thứ tự ưu tiên đã cấu hình. API quản lý rule cho phép tạo, cập nhật, xóa và sắp xếp thứ tự thực thi của các rule, đồng thời thực hiện kiểm tra tính hợp lệ của từng loại rule trước khi lưu vào cơ sở dữ liệu.

\subsubsection{Tạo rule}

Rule được tạo thông qua endpoint.



Request body gồm loại rule, độ ưu tiên và các tham số tương ứng.



Hệ thống hỗ trợ ba loại rule chính:

\begin{itemize}
    \item \texttt{USER\_ALLOWLIST};
    \item \texttt{ROLE\_TARGETING};
    \item \texttt{PERCENTAGE\_ROLLOUT}.
\end{itemize}

Các tham số của từng loại rule được lưu trong trường \texttt{parameters} dưới dạng JSONB để cho phép mở rộng mà không phải thay đổi lược đồ cơ sở dữ liệu \cite{postgresql_json_types}.

Khi nhận request tạo rule, backend thực hiện các bước:

\begin{enumerate}
    \item Kiểm tra flag configuration tồn tại;
    \item Kiểm tra feature flag chưa bị archive;
    \item Kiểm tra project đang ở trạng thái hoạt động;
    \item Validation dữ liệu theo từng loại rule;
    \item Gán version mới cho cấu hình;
    \item Ghi audit log.
\end{enumerate}

Response thành công.



Rule mới không được phép có độ ưu tiên trùng với rule khác trong cùng một flag configuration. Nếu xảy ra xung đột, backend có thể tự động dịch chuyển các rule phía sau hoặc từ chối request bằng mã lỗi \texttt{409 Conflict}. Trong mini project, hệ thống tự động điều chỉnh thứ tự để giảm thao tác thủ công của người quản trị.

\subsubsection{Cập nhật rule}

Rule được cập nhật bằng endpoint.



Request chỉ bao gồm các trường cần thay đổi.






Backend không cho phép thay đổi loại của một rule đã tồn tại. Nếu muốn chuyển từ \texttt{ROLE\_TARGETING} sang \texttt{PERCENTAGE\_ROLLOUT}, người quản trị phải tạo rule mới và xóa rule cũ. Quy tắc này giúp đơn giản hóa quá trình validation và bảo toàn lịch sử thay đổi.

Sau khi cập nhật thành công, backend:

\begin{enumerate}
    \item Kiểm tra dữ liệu mới;
    \item Tăng version của flag configuration;
    \item Ghi audit log;
    \item Invalidate cache evaluation.
\end{enumerate}

Response trả về dữ liệu rule mới nhất.



Việc cập nhật rule không thay đổi định danh của rule và không ảnh hưởng đến các rule khác nếu độ ưu tiên vẫn được giữ nguyên.

\subsubsection{Xóa rule}

Rule được xóa thông qua endpoint.



Sau khi xác nhận rule tồn tại, backend thực hiện:

\begin{enumerate}
    \item Xóa rule khỏi cơ sở dữ liệu;
    \item Sắp xếp lại thứ tự ưu tiên của các rule còn lại;
    \item Tăng version của flag configuration;
    \item Ghi audit log;
    \item Invalidate cache evaluation.
\end{enumerate}

Response thành công sử dụng mã trạng thái.



Nếu rule không tồn tại, hệ thống trả về.



Việc xóa rule chỉ ảnh hưởng đến một environment cụ thể vì mỗi environment sở hữu tập rule độc lập.

\subsubsection{Thay đổi độ ưu tiên}

Rule Evaluation Engine đánh giá các rule theo thứ tự ưu tiên từ nhỏ đến lớn. Rule đầu tiên thỏa mãn điều kiện sẽ quyết định kết quả evaluation và các rule phía sau không còn được kiểm tra.

Độ ưu tiên được cập nhật thông qua endpoint.






Hoặc endpoint hỗ trợ thay đổi trực tiếp vị trí của rule.



Ví dụ request.



Backend cập nhật toàn bộ thứ tự trong cùng một transaction để tránh trạng thái trung gian.

Sau khi cập nhật, các rule có thứ tự như sau:

\begin{center}
\begin{tabular}{cc}
\toprule
Rule & Priority \\
\midrule
Rule 3 & 1 \\
Rule 1 & 2 \\
Rule 2 & 3 \\
\bottomrule
\end{tabular}
\end{center}

Việc thay đổi thứ tự có ảnh hưởng trực tiếp đến kết quả evaluation. Ví dụ, một rule allowlist đặt trước percentage rollout sẽ luôn được áp dụng trước khi hệ thống thực hiện phân phối theo phần trăm. Do đó dashboard cần hiển thị rõ thứ tự thực thi để người quản trị tránh cấu hình sai \cite{launchdarkly_targeting_rules}.

\subsubsection{Validation tham số rule}

Mỗi loại rule có tập tham số và quy tắc validation riêng.

Đối với \texttt{USER\_ALLOWLIST}, request phải chứa danh sách người dùng:



Danh sách không được rỗng và không được chứa giá trị trùng lặp.

Đối với \texttt{ROLE\_TARGETING}, request phải chứa ít nhất một role hợp lệ:



Các role không được để trống và mỗi role chỉ xuất hiện một lần.

Đối với \texttt{PERCENTAGE\_ROLLOUT}, request có dạng.



Giá trị \texttt{percentage} phải nằm trong khoảng từ 0 đến 100.

Ngoài validation theo từng loại rule, backend còn kiểm tra:

\begin{itemize}
    \item kiểu dữ liệu của từng trường;
    \item số lượng phần tử tối đa trong danh sách;
    \item cấu trúc JSON hợp lệ;
    \item không tồn tại thuộc tính không được định nghĩa trong DTO.
\end{itemize}

Nếu request không hợp lệ, hệ thống trả về.



Ví dụ response.



Validation được thực hiện trước khi ghi dữ liệu xuống cơ sở dữ liệu nhằm ngăn các cấu hình không hợp lệ tham gia vào quá trình evaluation. Cách tiếp cận này giúp Rule Evaluation Engine luôn làm việc trên tập cấu hình hợp lệ, giảm khả năng phát sinh lỗi trong thời gian chạy và bảo đảm kết quả đánh giá nhất quán.

\subsection{Evaluation API}

Evaluation API là thành phần quan trọng nhất của nền tảng Feature Flag. API này được các ứng dụng khách gọi tại thời điểm chạy để xác định một feature có được bật hay không đối với một evaluation context cụ thể. Thiết kế API ưu tiên tính xác định, độ trễ thấp, khả năng mở rộng và hợp đồng dữ liệu ổn định nhằm đáp ứng yêu cầu tích hợp giữa nhiều ứng dụng khác nhau \cite{openfeature_flag_evaluation,openfeature_evaluation_context}.

\subsubsection{Evaluation request contract}

Evaluation được thực hiện thông qua endpoint:

\begin{lstlisting}
POST /v1/evaluate
\end{lstlisting}

Request body bao gồm khóa project, khóa feature flag và evaluation context:

\begin{lstlisting}
{
  "projectKey": "ecommerce-demo",
  "environmentKey": "production",
  "flagKey": "new-checkout",
  "context": {
    "targetingKey": "user-001",
    "roles": ["beta-customer"]
  }
}
\end{lstlisting}

Các trường có ý nghĩa như sau:

\begin{itemize}
    \item \texttt{projectKey}: xác định project chứa Feature Flag.
    \item \texttt{environmentKey}: xác định environment cần đánh giá.
    \item \texttt{flagKey}: khóa nghiệp vụ của Feature Flag.
    \item \texttt{context}: tập thông tin mô tả người dùng hoặc request hiện tại.
\end{itemize}

Trong evaluation context:

\begin{itemize}
    \item \texttt{targetingKey} là khóa định danh ổn định được sử dụng cho percentage rollout.
    \item \texttt{userId} phục vụ các rule theo người dùng.
    \item \texttt{roles} phục vụ role targeting.
    \item \texttt{attributes} là tập thuộc tính mở rộng để hỗ trợ các rule trong tương lai.
\end{itemize}

Trong ba loại rule được hỗ trợ của mini project:

\begin{itemize}
    \item \texttt{USER\_ALLOWLIST} sử dụng \texttt{userId};
    \item \texttt{ROLE\_TARGETING} sử dụng \texttt{roles};
    \item \texttt{PERCENTAGE\_ROLLOUT} sử dụng \texttt{targetingKey}.
\end{itemize}

Evaluation request không chứa thông tin cấu hình của Feature Flag. Toàn bộ cấu hình được truy xuất từ cơ sở dữ liệu dựa trên project, environment và flag tương ứng. Cách tách biệt này giúp ứng dụng khách chỉ cung cấp evaluation context, trong khi toàn bộ logic quyết định được quản lý tập trung trên nền tảng Feature Flag.

Backend thực hiện validation request trước khi đánh giá:

\begin{itemize}
    \item các trường bắt buộc không được để trống;
    \item project và flag key phải đúng định dạng;
    \item context phải là đối tượng JSON hợp lệ;
    \item \texttt{roles} phải là mảng chuỗi;
    \item \texttt{attributes} phải là object JSON.
\end{itemize}

Sau khi validation thành công, Evaluation Engine tải snapshot cấu hình tương ứng và thực hiện đánh giá theo thứ tự ưu tiên đã thiết kế.

\subsubsection{Evaluation response contract}

Response của Evaluation API trả về toàn bộ thông tin cần thiết để ứng dụng khách quyết định hành vi của tính năng.

Ví dụ:

\begin{lstlisting}
{
  "projectKey": "ecommerce-demo",
  "flagKey": "new-checkout",
  "enabled": true,
  "variant": "on",
  "reason": "ROLE_MATCH",

\subsection{Mô hình phản hồi lỗi}

Hệ thống sử dụng một mô hình phản hồi lỗi thống nhất cho toàn bộ REST API nhằm giúp ứng dụng khách xử lý lỗi một cách nhất quán. Mỗi phản hồi lỗi đều bao gồm mã lỗi nghiệp vụ, thông báo mô tả, danh sách chi tiết (nếu có) và request ID để hỗ trợ truy vết. Việc chuẩn hóa cấu trúc phản hồi giúp giảm sự phụ thuộc vào từng endpoint cụ thể và đơn giản hóa việc tích hợp SDK hoặc frontend dashboard \cite{owasp_rest_security}.

\subsubsection{Cấu trúc lỗi thống nhất}

Mọi lỗi đều sử dụng cùng một cấu trúc JSON.




Ý nghĩa các trường:

\begin{itemize}
    \item \texttt{code}: mã lỗi nghiệp vụ.
    \item \texttt{message}: mô tả ngắn gọn của lỗi.
    \item \texttt{details}: danh sách lỗi chi tiết.
    \item \texttt{requestId}: định danh duy nhất của request.
\end{itemize}

Các mã lỗi nghiệp vụ phổ biến gồm:

\begin{center}
\begin{tabular}{ll}
\toprule
Code & Ý nghĩa \\
\midrule
VALIDATION\_ERROR & Dữ liệu đầu vào không hợp lệ \\
NOT\_FOUND & Không tìm thấy tài nguyên \\
CONFLICT & Xung đột dữ liệu \\
INTERNAL\_ERROR & Lỗi nội bộ hệ thống \\
\bottomrule
\end{tabular}
\end{center}

HTTP status code được sử dụng để biểu diễn loại lỗi ở mức giao thức, trong khi trường \texttt{code} giúp client phân biệt chi tiết nguyên nhân xử lý.

\subsubsection{Validation error}

Nếu request không thỏa mãn các ràng buộc validation, API trả về.












Trường \texttt{details} có thể chứa nhiều lỗi cùng lúc để client có thể hiển thị toàn bộ các trường cần sửa mà không phải gửi lại nhiều request liên tiếp.

Validation được thực hiện trước khi truy cập cơ sở dữ liệu nhằm giảm tải cho hệ thống và ngăn chặn các thao tác nghiệp vụ trên dữ liệu không hợp lệ.

\subsubsection{Not found và conflict}

Nếu tài nguyên được yêu cầu không tồn tại, hệ thống trả về.









Đối với các trường hợp xung đột dữ liệu hoặc vi phạm ràng buộc duy nhất, hệ thống trả về.



Ví dụ khi tạo project với project key đã tồn tại.



Các tình huống thường dẫn đến lỗi \texttt{409 Conflict} gồm:

\begin{itemize}
    \item project key đã tồn tại;
    \item environment key trùng trong cùng project;
    \item flag key trùng trong cùng project;
    \item cập nhật cấu hình với version cũ;
    \item thao tác không phù hợp với trạng thái hiện tại của tài nguyên.
\end{itemize}

Việc phân biệt rõ giữa \texttt{404} và \texttt{409} giúp client có thể đưa ra hành vi xử lý phù hợp đối với từng loại lỗi.

\subsubsection{Internal error}

Các lỗi ngoài dự kiến trong quá trình xử lý được ánh xạ thành:






Các nguyên nhân có thể gồm:

\begin{itemize}
    \item lỗi kết nối cơ sở dữ liệu;
    \item lỗi cache;
    \item exception chưa được xử lý;
    \item lỗi trong quá trình thực thi transaction.
\end{itemize}

Response không trả về stack trace, câu lệnh SQL hoặc các thông tin nội bộ của hệ thống nhằm tránh làm lộ chi tiết triển khai. Thông tin kỹ thuật đầy đủ chỉ được ghi vào log phía máy chủ để phục vụ việc điều tra và khắc phục sự cố \cite{owasp_rest_security,owasp_logging}.

Đối với Evaluation API, lỗi nội bộ không sử dụng phản hồi HTTP 500 nếu request đã hợp lệ. Thay vào đó, Evaluation Engine trả về kết quả an toàn với \texttt{enabled = false} và reason code \texttt{ERROR}, nhất quán với nguyên tắc fail-safe của luồng evaluation.

\subsubsection{Request ID và khả năng truy vết}

Mỗi HTTP request được gán một định danh duy nhất gọi là request ID. Giá trị này được tạo ngay khi request đi vào hệ thống và được truyền xuyên suốt toàn bộ quá trình xử lý.

Request ID được:

\begin{itemize}
    \item trả về trong mọi response lỗi;
    \item ghi vào audit log;
    \item ghi vào application log;
    \item liên kết với các thao tác mutation trong cùng request.
\end{itemize}




Khi người dùng báo cáo lỗi, quản trị viên chỉ cần sử dụng request ID để tìm toàn bộ log liên quan trên máy chủ, bao gồm thông tin request, exception phát sinh và các audit log tương ứng. Cơ chế này giúp rút ngắn thời gian điều tra sự cố và tăng khả năng truy vết trong quá trình vận hành.

Request ID được xem là metadata của request và không mang ý nghĩa nghiệp vụ. Giá trị này không được sử dụng để xác thực người dùng hoặc xác định tài nguyên trong hệ thống, mà chỉ phục vụ mục đích quan sát và chẩn đoán lỗi.

\subsection{Tài liệu hóa API}

Bên cạnh việc thiết kế API rõ ràng, hệ thống cung cấp tài liệu API tự động nhằm hỗ trợ phát triển, kiểm thử và tích hợp với các ứng dụng khách. Tài liệu được sinh trực tiếp từ mã nguồn backend thông qua chuẩn OpenAPI, giúp bảo đảm tính đồng nhất giữa tài liệu và triển khai thực tế.

Trong quá trình phát triển, mọi thay đổi đối với DTO, endpoint hoặc response đều được phản ánh tự động trong tài liệu API, giảm nguy cơ tài liệu bị lỗi thời so với hệ thống đang triển khai.

\subsubsection{OpenAPI và Swagger}

Hệ thống sử dụng chuẩn OpenAPI để mô tả toàn bộ REST API. Trên nền tảng này, Swagger UI được tích hợp nhằm cung cấp giao diện trực quan để xem tài liệu và thử nghiệm các endpoint.

Sau khi backend khởi động, tài liệu API có thể được truy cập thông qua:

\begin{lstlisting}
/api/docs
\end{lstlisting}

Swagger UI hiển thị:

\begin{itemize}
    \item danh sách endpoint;
    \item HTTP method;
    \item request body;
    \item response schema;
    \item HTTP status code;
    \item ví dụ request và response.
\end{itemize}

Các endpoint được nhóm theo chức năng, ví dụ:

\begin{itemize}
    \item Projects;
    \item Environments;
    \item Feature Flags;
    \item Flag Configurations;
    \item Rules;
    \item Evaluation;
    \item Audit Logs;
    \item Statistics.
\end{itemize}

Việc nhóm endpoint theo tài nguyên giúp người phát triển dễ dàng tìm kiếm và hiểu cấu trúc API.

OpenAPI cũng cho phép sinh SDK hoặc client code tự động cho nhiều ngôn ngữ lập trình, giảm công sức tích hợp giữa nền tảng Feature Flag và các ứng dụng khách.

\subsubsection{Mô tả request và response schema}

Request schema:

\begin{lstlisting}

  "context": { "targetingKey": "string", "roles": ["string"] }

Response schema:

\begin{lstlisting}
{

    \item giá trị enum nếu có;
    \item mô tả ý nghĩa của từng trường.
\end{itemize}

Nhờ vậy, frontend, SDK và các ứng dụng tích hợp có thể hiểu chính xác hợp đồng dữ liệu mà không cần tham khảo mã nguồn backend.
