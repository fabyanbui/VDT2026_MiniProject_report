\section{Kiến trúc tổng thể của hệ thống}

Phần này trình bày kiến trúc ở mức hệ thống dựa trên sơ đồ tổng thể và source code hiện tại của repository. Các chi tiết về mô hình dữ liệu, Rule Evaluation Engine, API, cache, kiểm thử và bảo mật được trình bày ở các mục chuyên sâu phía sau.

\subsection{Các thành phần chính}

Hình~\ref{fig:system-overall-architecture} mô tả hệ thống theo ba lớp chính: client/frontend, backend API và persistence/cache. Backend NestJS là ranh giới truy cập duy nhất cho cả luồng quản trị và luồng evaluation; Rule Evaluation Engine được tách khỏi controller để giữ logic quyết định xác định, dễ kiểm thử và không phụ thuộc giao diện.

\subsubsection{Frontend / Client layer}

Lớp client gồm \texttt{apps/admin}, \texttt{apps/demo} và \texttt{packages/js-sdk}. Admin Dashboard là React/Vite SPA cho project, flag, rule, group, audit log, history, RBAC demo và statistics. Demo Application mô phỏng ứng dụng thương mại điện tử nhỏ và dùng kết quả evaluation để bật hoặc ẩn tính năng. \texttt{@ffp/js-sdk} chuẩn hóa cách gọi Evaluation API, validate response, xử lý timeout/lỗi mạng và trả fallback fail-closed cho ứng dụng web.

\subsubsection{Backend API và lớp bảo vệ}

Backend nằm trong \texttt{apps/backend} và được triển khai bằng NestJS với global prefix \texttt{/v1}, DTO validation, Swagger, CORS theo admin/demo origin và request context middleware. \texttt{AuthModule} cung cấp demo authentication guard và permission guard cho control-plane endpoint; Health API và Evaluation API được đánh dấu public để phục vụ runtime evaluation.

\subsubsection{Management modules}

Các module quản trị gồm project, feature flag, flag rule, flag group, sample user, audit log/history và statistics. Mutation quan trọng đi qua validation, permission check, Prisma transaction, audit log append-only và cache invalidation. Cách tổ chức này giữ logic quản trị tập trung ở backend thay vì phân tán sang Dashboard.

\subsubsection{Evaluation runtime}

Data plane bắt đầu tại \texttt{POST /v1/evaluate}. \texttt{EvaluationService} lấy snapshot từ cache hoặc repository, gọi hàm thuần \texttt{evaluateFlag}, rồi trả kết quả gồm \texttt{projectKey}, \texttt{flagKey}, \texttt{enabled}, \texttt{variant}, \texttt{reason} và \texttt{matchedRuleId}. Engine áp dụng precedence: archived, config disabled, group kill switch, flag kill switch, global on, user allowlist, role targeting, percentage rollout và default off.

\subsubsection{Persistence, cache và deployment}

PostgreSQL là nguồn sự thật cho project, environment, flag, config, rule, group, audit log, sample user và aggregate metric. Evaluation Snapshot Cache chỉ lưu cấu hình cần cho evaluation, không lưu context người dùng hay kết quả theo user; provider có thể là \texttt{memory}, \texttt{none} hoặc optional \texttt{redis}. Repository hỗ trợ chạy bằng npm workspace hoặc Docker Compose với PostgreSQL, migration, seed, backend, admin, demo, demo staging và optional Redis.

\subsection{Control plane và data plane}

Kiến trúc tách \textit{control plane} và \textit{data plane} vì Feature Flag có hai loại tải khác nhau: thay đổi cấu hình ít hơn nhưng evaluation có thể xảy ra liên tục từ ứng dụng tích hợp \cite{launchdarkly_feature_flags,unleash_feature_flag_best_practices}. Control plane gồm Admin Dashboard, Auth/Permission Guards, Management API, Audit Log/History và Cache Invalidation. Data plane gồm Evaluation API, Snapshot Cache, Rule Evaluation Engine và Evaluation Metrics.

    \centering

Trong control plane, mọi mutation quan trọng được backend kiểm tra quyền, validate dữ liệu, ghi PostgreSQL và tạo audit entry với before/after snapshot. Trong data plane, ứng dụng khách chỉ gửi project key, environment key nếu có, flag key và context không nhạy cảm; Evaluation API đọc snapshot cấu hình, chạy engine và trả reason code. Cache và metric chỉ là tối ưu/quan sát best-effort nên không được làm thay đổi quyết định bật/tắt.

\subsection{Luồng quản trị Feature Flag}

Người dùng quản trị chọn project trên Dashboard rồi tạo/sửa flag, đổi lifecycle, cấu hình status/serving mode theo environment, thay thế rule, gán group hoặc bật kill switch. Dashboard chỉ gửi request và hiển thị trạng thái; backend chịu trách nhiệm kiểm tra quyền, kiểm tra dữ liệu, lưu bằng Prisma transaction và ghi audit log. Rule được lưu dưới dạng \texttt{USER\_ALLOWLIST}, \texttt{ROLE\_TARGETING} hoặc \texttt{PERCENTAGE\_ROLLOUT} với \texttt{priority} và tham số \texttt{JSONB}.

Sau khi mutation commit, cache invalidator xóa snapshot liên quan để evaluation tiếp theo không dùng cấu hình cũ. Ví dụ, thay đổi flag config/rule sẽ invalidation snapshot của flag; gán group hoặc bật group kill switch sẽ invalidation các flag bị ảnh hưởng. Nhờ vậy, thay đổi từ Dashboard có thể được truy vết qua audit/history và phản ánh ở Demo Application mà không cần redeploy.

\subsection{Luồng đánh giá Feature Flag}

Luồng evaluation bắt đầu từ Demo Application hoặc SDK và kết thúc bằng một response có reason code. Evaluation API không thay đổi cấu hình và không ghi audit log quản trị. Hình~\ref{fig:evaluation-flow} mô tả flow chính: nhận request, lấy snapshot từ cache hoặc PostgreSQL, gọi Rule Evaluation Engine, ghi metric best-effort và trả kết quả cho client.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{\detokenize{Images/mermaid/Luồng đánh giá Feature Flag.png}}
    \caption{Luồng đánh giá Feature Flag từ ứng dụng khách đến Rule Evaluation Engine}

Nếu snapshot không tồn tại, service trả \texttt{enabled=false} với \texttt{reason=NOT\_FOUND}; nếu có lỗi bất thường, hệ thống fail-closed với \texttt{reason=ERROR}. Nếu snapshot hợp lệ, engine xét các điều kiện terminal trước rồi mới xét global on và rule targeting. Percentage rollout dùng stable hashing trên project key, flag key và targeting key để kết quả lặp lại ổn định cho cùng một context.

\subsection{Luồng tích hợp ứng dụng khách}

Ứng dụng khách có thể gọi trực tiếp Evaluation API hoặc dùng \texttt{@ffp/js-sdk}. Trong project này, Demo Application dùng SDK để cấu hình \texttt{baseUrl}, \texttt{projectKey}, optional \texttt{environmentKey}, timeout và \texttt{fetch}; sau đó gọi \texttt{evaluate}, \texttt{isEnabled} hoặc \texttt{getVariant}. Context chỉ là đầu vào targeting, thường gồm \texttt{targetingKey}, \texttt{userId} mẫu, \texttt{roles} và \texttt{attributes}, không phải bằng chứng phân quyền.

Khi API timeout, lỗi mạng, HTTP lỗi, JSON sai shape hoặc response không khớp project/flag, SDK trả fallback an toàn: \texttt{enabled=false}, \texttt{variant=off}, \texttt{reason=ERROR} và \texttt{errorSource=CLIENT}. Quy tắc này ngăn lỗi hạ tầng vô tình mở tính năng chưa sẵn sàng.

\subsection{Lựa chọn công nghệ}

NestJS được chọn cho backend vì hỗ trợ module hóa, dependency injection, guard/pipe/filter, Swagger và Jest, phù hợp với yêu cầu tách controller, service, repository và domain evaluation. React/Vite được chọn cho Admin Dashboard và Demo Application vì nhẹ, dễ chia component và phù hợp npm workspace. PostgreSQL và Prisma được dùng để có transaction, khóa ngoại, unique constraint, \texttt{JSONB}, migration và data access có kiểu.

Cache snapshot dùng in-memory mặc định để đơn giản cho demo một instance; optional Redis thể hiện hướng mở rộng khi cần cache chia sẻ. JavaScript SDK được tách thành package riêng để ổn định contract tích hợp và đóng gói fail-closed behavior ở client. Docker Compose được chọn để khởi chạy lặp lại toàn bộ PostgreSQL, migration, seed, backend, admin và demo cho chấm điểm/trình diễn. Các phương án như tách microservice evaluation, message broker hoặc local-evaluation SDK phức tạp được để ngoài phạm vi vì làm tăng chi phí vận hành so với mục tiêu mini project.
